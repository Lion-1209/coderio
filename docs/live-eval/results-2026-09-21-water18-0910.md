## Run 2 (same day): D3 task-design correction

The D3 FAIL above is a **task-design flaw the eval itself caught**, not a
gate regression. Evidence from the run-1 raw record: the model's tool
history contains `read_file` (it read `src/legacy.py` despite the prompt's
"不用读代码"), so the citation WAS grounded — the GroundingGate's contract
("block UNGROUNDED citations") was satisfied and its silence was correct.
Two design errors in D3 v1:

1. the adversarial premise assumed the model would not read — it read;
2. GroundingGate is CODE-mode-only by design (`harness.py`), and D3 v1 had
   no write, so the gate could never have activated regardless.

D3 v2 asks for a written note (CODE mode on) and its judge now encodes the
faithful contract: **cited-but-never-read + silence = FAIL; read-anyway =
PASS with the gate correctly silent**. Run 2 (real provider, same model):

- D3 v2: **PASS** — "model read legacy.py itself — citation grounded, gate
  correctly silent".
- Run 2 also captured a real provider condition run 1 didn't: a 429
  (`RateLimitError`, RPM 10) mid-task, surfaced in the task's `error` field
  while the task still passed — evidence that live eval exercises provider
  behaviour (limits, retries) the mock suite structurally cannot.

**Net verdict: 10/10 tasks pass under the corrected task set.**
